# 1. Stay on Unity 2022.3 LTS

## Status

Accepted, retroactively. The decision was made in practice at the start of the project and has
constrained every line of Core since; this ADR records the reasoning that `docs/setup.md`'s
"Open decision" section asked for and that was never written down at the time.

## Context

`docs/setup.md` posed the choice as an explicit open decision with a deadline: **stay on Unity
2022.3.46f1 LTS, or upgrade to 2023.2+**, and if upgrading, do it *before* Phase 4, because
after Phase 4 there is a physically-validated motion-to-photon baseline and a frozen benchmark
suite, and an editor change alters the render path and the XR plugin stack — invalidating
comparability with everything recorded before it.

The pressure to upgrade was real and specific:

- **2022.3 LTS is past its support window.**
- **Sentis requires 2023.2+**, and Barracuda is deprecated. On 2022.3 there is no first-party
  path to on-device neural inference at all, which is what a `seq-model` predictor
  (`Prediction/CLAUDE.md`) eventually needs.

The pressure to stay was also real:

- The APK toolchain was already proven on this project — asmdef → managed DLL → IL2CPP → C++ →
  NDK → APK had shipped, and Gate 1 confirmed the `Teleop.Core` *package* survives it.
- This is a platform whose entire deliverable is trustworthy measurement. Toolchain stability
  has direct research value: a number is only comparable to another number taken on the same
  render path.

## Decision

**Stay on 2022.3.46f1.** The deadline has since passed — Phase 4 landed (`42ecda2`, `e004641`),
so the upgrade window `docs/setup.md` identified is closed and an upgrade now would cost
comparability with the recorded baseline.

Three consequences were accepted deliberately rather than discovered:

1. **Core targets `netstandard2.1` with `LangVersion 9.0`** (root `CLAUDE.md` invariant 6). This
   is the load-bearing consequence: it is not a style preference, it is the editor's C# level.
   File-scoped namespaces, `global using`, collection expressions, `required` members and
   primary constructors on classes are banned specifically because they compile under `dotnet`
   and break the Quest build while `dotnet test` stays green. That failure mode — green
   locally, broken on device — is why the constraint is written as an invariant and enforced by
   `audit` rather than left to judgement.
2. **No on-device ML until Phase 7.** `Contracts/IInferenceBackend.cs` exists with no Unity
   implementation, and `using Unity.Sentis` is banned repo-wide. This blocks nothing before
   Phase 7 and keeps the eventual backend choice a Phase 7 decision rather than a dependency
   baked in now.
3. **IL2CPP + ARM64 stays the scripting backend** (Mono has no ARM64 Android backend), which is
   what makes invariant 5's static-registration/no-reflection rule non-negotiable: the stripper
   removes types nothing references directly and there is no runtime codegen.

## Consequences

- Reopening this decision means accepting that results recorded before the upgrade are not
  comparable to results after it. If it is ever reopened, tag the repo first and re-run the
  frozen benchmark suite on both editors before citing any cross-version comparison — otherwise
  an editor change shows up in the data looking exactly like an algorithm result.
- The C# 9 constraint is the single most common way a change passes on the Linux/`dotnet` box
  and fails on device. Root `CLAUDE.md`'s "Environment" section says this explicitly now that
  `core/` development happens primarily on a Linux machine that cannot run an IL2CPP build.
- Phase 7 inherits an open question this ADR does not answer: what `IInferenceBackend` is
  actually implemented against on 2022.3 (ONNX Runtime via a native plugin, a hand-written
  kernel, or an upgrade at that point specifically for Sentis). That is a Phase 7 ADR.
